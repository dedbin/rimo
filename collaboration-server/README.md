# Сервер совместной работы

Отдельный долгоживущий процесс Hocuspocus. Node.js 22+, PostgreSQL и миграции проекта обязательны. Запуск: `npm run collaboration`. Переменные окружения читаются из `.env.local` при локальном запуске; контейнер передаёт их при старте.

## Размещение и доступ

- На одну БД и схему допускается **ровно один writer**. PostgreSQL advisory lock не позволяет случайно запустить второй процесс. Потеря соединения, удерживающего lock, завершает процесс; тихое зависание проверяется heartbeat с дедлайном.
- `COLLABORATION_HOST` по умолчанию `127.0.0.1`; в контейнере нужен `0.0.0.0`. `COLLABORATION_PORT` по умолчанию `1234`.
- Cookie Better Auth передаётся через тот же домен. Production proxy направляет `/collaboration` в этот процесс. `Origin` обязан точно входить в `trustedOrigins` из серверной конфигурации.
- При подключении и затем каждые пять секунд проверяются сессия и текущий ACL. Проверка имеет дедлайн три секунды; недоступная БД прекращает доступ. Viewer не может писать даже прямым CRDT сообщением.
- `GET /healthz` проверяет доступность БД и отсутствие неразрешённых ошибок записи.

## Сохранение и ограничения

Снимки Yjs хранятся в `board_documents`. Состояние и snapshot захватываются синхронно, затем выполняются транзакция и `COMMIT`. Только после этого отправляется `persisted {revision,snapshot,savedAt}`. Клиент сравнивает Yjs snapshots, включая удаления. Обычная синхронизация WebSocket не подтверждает запись на диск.

При ошибке записи документ остаётся в памяти, клиенты получают `persistence-error`, а сервер повторяет запись с ограниченной частотой. Изменения без подтверждения могут пропасть при аварийном завершении процесса; интерфейс не показывает их сохранёнными.

Начальные пределы: 50 подключений, 10 подключений на доску, 10 соединений с правом записи и 10 открытых документов на процесс; документ до 5 МиБ и 10 000 объектов. Входящая очередь каждого соединения ограничена 32 кадрами и 6 МиБ; частота и байты считаются при получении, до очереди Hocuspocus. Эти пределы являются защитными настройками, а не доказанной вместимостью сервера.

Изменение документа сначала проверяется в отдельном Y.Doc, а применение сериализовано в пределах комнаты. Стоимость копирования растёт с документом; перед увеличением вместимости требуется профилирование контрольной сцены.

## Проверки

```powershell
node --env-file=.env.local node_modules/vitest/vitest.mjs run collaboration-server/__tests__
```

Для PostgreSQL проверок нужен `DATABASE_URL`; без него эти отдельные тесты пропускаются. Проверки создают и удаляют только собственные схемы `rimo_ws_test_*`. Аварийная проверка запускает отдельный процесс, ждёт DB ACK, завершает его через `SIGKILL` и проверяет восстановление другим процессом. Остальные проверки используют настоящие WebSocket подключения и контролируемые хранилище/ACL для воспроизводимых отказов.
