# Сервер совместной работы

Отдельный долгоживущий процесс Hocuspocus. Node.js 22+, PostgreSQL и миграции проекта обязательны. После `npm run build` запуск: `npm run collaboration`. Переменные окружения читаются из `.env.local` при локальном запуске; контейнер передаёт их при старте.

`scripts/build-collaboration.mjs` входит в postbuild и собирает собственные TypeScript-модули в `dist/collaboration/index.mjs` с отдельной source map. Зависимости остаются внешними: native Node загружает их ESM exports и один Yjs, без runtime-трансляции через tsx. В Docker и managed Playwright запускается тот же compiled entry. Модель, полная валидация, ACL и протокол сохранения общие с исходниками; сборка не заменяет их ускоренным вариантом. Каталог `dist` не хранится в Git. Для разработки с прямым исполнением TypeScript остаётся `npm run collaboration:dev`.

Команды production запускают Node с `--enable-source-maps`: ошибки compiled
entry указывают исходный TypeScript через отдельную связанную source map.

## Размещение и доступ

- На одну БД и схему допускается **ровно один writer**. PostgreSQL advisory lock не позволяет случайно запустить второй процесс. Потеря соединения, удерживающего lock, завершает процесс; тихое зависание проверяется heartbeat с дедлайном.
- `COLLABORATION_HOST` по умолчанию `127.0.0.1`; в контейнере нужен `0.0.0.0`. `COLLABORATION_PORT` по умолчанию `1234`.
- Cookie Better Auth передаётся через тот же домен. Production proxy направляет `/collaboration` в этот процесс. `Origin` обязан точно входить в `trustedOrigins` из серверной конфигурации.
- При подключении проверяется cookie Better Auth. Повторная проверка сессии и ACL выполняется одним SQL-запросом без кеша. Она устаревает через пять секунд от начала предыдущего запроса; периодический скан раз в секунду обновляет только устаревшие соединения. Монотонный таймер не зависит от перевода системных часов. Дедлайн запроса остаётся три секунды; недоступная БД прекращает доступ. Viewer не может писать даже прямым CRDT сообщением.
- `GET /healthz` проверяет доступность БД и отсутствие неразрешённых ошибок записи.

## Сохранение и ограничения

Снимки Yjs хранятся в `board_documents`. Состояние и snapshot захватываются синхронно, затем выполняются транзакция и `COMMIT`. Только после этого отправляется `persisted {revision,snapshot,savedAt}`. Клиент сравнивает Yjs snapshots, включая удаления. Обычная синхронизация WebSocket не подтверждает запись на диск.

При ошибке записи документ остаётся в памяти, клиенты получают `persistence-error`, а сервер повторяет запись с ограниченной частотой. Изменения без подтверждения могут пропасть при аварийном завершении процесса; интерфейс не показывает их сохранёнными.

Начальные пределы: 50 подключений, 10 подключений на доску, 10 соединений с правом записи и 10 открытых документов на процесс; документ до 5 МиБ и 10 000 объектов. Входящая очередь каждого соединения ограничена 64 кадрами и 6 МиБ, сумма очередей процесса — 32 МиБ. Частота ограничена 120 сообщениями и 2 МиБ в секунду на соединение. Эти пределы являются защитными настройками, а не доказанной вместимостью сервера.

Запас 64 кадров позволяет переждать допустимую задержку проверки прав без изменения её трёхсекундного deadline: очередь32 при обычных cursor20Гц и изменениях2Гц заполнялась раньше. Реальный SDK-тест проверяет отказ при32, drain/ACK при64 и отказ65-го удерживаемого кадра. Увеличение буфера не ускоряет обработку и требует отдельного полного нагрузочного прогона.

Учёт устанавливается через публичный `handleConnection` экземпляра Hocuspocus до регистрации WebSocket message listener, поэтому охватывает и очередь SDK до завершения авторизации. Начальный Auth ограничен 4 КиБ и контрактом cookie-аутентификации приложения. Резерв остаётся занят до освобождения соответствующей очереди; закрытые соединения с ещё выполняющимся обработчиком входят в общий предел 50. Собственное событие guard `collaboration_receive_limit` содержит только вид отказа и числовые счётчики, без комнаты, пользователя или содержимого кадра. Это не описание всех сообщений журнала SDK. Квота кадра ограничивает входящие байты, но не гарантирует верхнюю границу памяти после декодирования Yjs.

Клиентский `configureOfflineSync` не помещает SyncUpdate в транспортную очередь закрытого сокета. Изменения остаются в Y.Doc и передаются обычным state-vector handshake при восстановлении связи. При OPEN сообщения всегда отправляются, включая период до `synced`; Auth, awareness и остальные сообщения сохраняют штатное поведение SDK.

Изменение сначала проходит полную проверку схемы в отдельном Y.Doc, применение
сериализовано в пределах комнаты. Проверочная копия переиспользуется только при
совпадении полного бинарного состояния с авторитетным документом, включая
отложенные structs и delete sets; при расхождении или отказе она удаляется.
Проверка и кодирование по-прежнему зависят от размера документа: перед
увеличением вместимости нужен замер контрольной сцены.

Имя комнаты — канонический UUID в нижнем регистре. Слот новой комнаты
резервируется синхронно после авторизации, до загрузки документа; одновременные
подключения не обходят общий предел. При ошибке загрузки, истечении резерва или
остановке ресурсы освобождаются. Адаптер создания документа зависит от API
закреплённого Hocuspocus; при обновлении SDK повторите проверки границ:

```sh
npm run test:integration -- __tests__/room-identity.integration.test.ts collaboration-server/__tests__/room-admission.test.ts __tests__/validation-cache
```

## Проверки

```powershell
node --env-file-if-exists=.env.local scripts/test-integration.mjs collaboration-server/__tests__
```

Для PostgreSQL проверок используйте `scripts/test-integration.mjs` с явно заданным `RIMO_TEST_DATABASE_URL`. Launcher передаёт этот адрес дочерним тестам как `DATABASE_URL`; рабочего адреса по умолчанию нет. Проверки создают и удаляют только собственные схемы `rimo_ws_test_*`. Аварийная проверка запускает отдельный процесс, ждёт DB ACK, завершает его через `SIGKILL` и проверяет восстановление другим процессом. Остальные проверки используют настоящие WebSocket подключения и контролируемые хранилище/ACL для воспроизводимых отказов.

Compiled runtime проверяется отдельно:

```sh
node node_modules/vitest/vitest.mjs run __tests__/compiled-collaboration.test.ts
node --env-file-if-exists=.env.local scripts/test-integration.mjs __tests__/compiled-collaboration.integration.test.ts
```

Первая команда собирает native smoke и проверяет идентичность Yjs/Hocuspocus/codec без сети. Вторая через `test-integration.mjs` требует отдельный `RIMO_TEST_DATABASE_URL` и запускает настоящий compiled index в отдельном процессе со своей схемой `rimo_compiled_test_*` и временным loopback-портом. Она проверяет реальные Better Auth cookies, persisted ACK против PostgreSQL, отказ некорректного XML, отзыв приглашения и сохранность принятого, но ещё не подтверждённого изменения после graceful restart. Рабочий Compose для этого не перезапускается.
