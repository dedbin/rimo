# Rimo

Rimo — совместная бесконечная доска для занятий и командной работы. Владелец создаёт постоянную доску, а ученики присоединяются по отзываемой ссылке без регистрации.

Текущая переработка сохраняет SVG-редактор и привычное расположение инструментов. Аккаунты, данные и совместная работа размещаются на собственной инфраструктуре: **Next.js 15, Better Auth, PostgreSQL 18, Yjs и Hocuspocus**.

## Возможности

- Создание, поиск, переименование и удаление досок, избранное.
- Гостевые приглашения с ограниченным сроком, роли редактора и зрителя, изменение прав и отзыв активного доступа.
- Фигуры, рисование, текст, стикеры, изображения, выбор, перемещение, изменение размеров и масштабирование.
- Совместные курсоры и выделения. Групповое перемещение записывается одной транзакцией; локальная отмена сохраняет независимые изменения другого участника.
- Изображения с проверкой фактического содержимого, ограничением размера и выдачей только участникам доски.
- Сохранение в PostgreSQL. Надпись «Сохранено» подтверждает запись снимка в БД, включая удаления.
- Совместный rich text: жирный, курсив, списки, код, ограниченный Markdown и редактируемые inline/block формулы LaTeX.
- Перенос изображений и форматированного текста между досками с проверкой исходного доступа и собственными файлами получателя.
- Именованные области страниц, предпросмотр фиксированной ревизии и векторный PDF с копируемым русским текстом.
- Архив `.rimo` с изображениями, форматированием, LaTeX и порядком фреймов; восстановление создаёт новую доску.

Полный объём и критерии приёмки находятся в [плане развития](plan/rimo-development-plan-2026-10-26.md); текущая работа отслеживается в [рабочем плане](plan/task_plan.md). Вместимость больших групп и длительные нагрузочные профили принимаются отдельно по измерениям, а не по выставленным защитным лимитам.

## Запуск через Docker

Нужны Docker Engine с Compose и Node.js 22.12+ для генерации конфигурации. Проверенный тестовый стек использует Linux-контейнеры.

```bash
node scripts/setup-env.mjs http://localhost:3080
docker compose up --build -d --wait
```

Откройте [localhost:3080](http://localhost:3080). Скрипт создаёт `.env` с независимыми случайными секретами и отказывается перезаписывать существующий файл. Секреты передаются контейнерам при запуске и исключены из образа.

Для собственного домена:

```bash
node scripts/setup-env.mjs https://board.example.com
```

Направьте домен на сервер и откройте порты 80/443. Caddy обслуживает HTTPS и WebSocket. PostgreSQL и Hocuspocus напрямую наружу не публикуются. Пример параметров — [config/environment.example](config/environment.example).

Стек состоит из PostgreSQL, одноразового процесса миграций, приложения, сервера совместной работы, отдельного PDF worker и Caddy. Worker работает в своей внутренней сети без доступа к БД, с непривилегированным пользователем, Chromium sandbox и ограничением памяти. Данные PostgreSQL и изображения находятся в постоянных именованных томах. Проверка состояния:

```bash
docker compose ps
docker compose logs --tail 100 app collaboration
```

## Создание владельца

Для создания аккаунта нажмите «Регистрация» или «Попробовать бесплатно» и
укажите имя, почту и пароль от 12 символов. Затем введите шестизначный код из письма.
Код действует 10 минут, допускает 5 попыток; повторная отправка доступна через минуту.
После подтверждения выполнится вход с введённым паролем. Последующие входы — по почте и паролю.
В форме можно переключиться на вход в существующий аккаунт. Общий лимит
`MAX_OWNERS` (по умолчанию 6) проверяется при активации аккаунта;
незавершённые регистрации не занимают места. Существующие владельцы подтверждают
почту один раз перед продолжением работы, сохраняя свои места, доски и права;
новый аккаунт не получает доступ к чужим доскам.

Оператор также может создать владельца через CLI. В PowerShell7:

```powershell
$env:OWNER_EMAIL = 'you@example.org'
$env:OWNER_NAME = 'Владелец'
$env:OWNER_PASSWORD = Read-Host 'Пароль, минимум 12 символов' -MaskInput
docker compose run --rm --no-deps -e OWNER_EMAIL -e OWNER_NAME -e OWNER_PASSWORD app node --import=tsx scripts/create-owner.ts
Remove-Item Env:OWNER_PASSWORD
```

Затем нажмите «Войти», введите почту и пароль и подтвердите адрес кодом из письма.
Для локальной разработки тот же CLI запускается командой `npm run owner:create` с указанными переменными окружения.

### Отправка кодов и обновление существующего сервиса

В окружении приложения задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`
и `MAIL_FROM` (чистый адрес отправителя, например `no-reply@example.com`). Используйте
разрешённый провайдером адрес и его настройки домена SPF/DKIM. Порт по умолчанию —
587 с обязательным STARTTLS, порт 465 использует TLS с начала соединения.
Реквизиты хранятся в приватном окружении сервера. Compose передаёт их только
приложению и предоставляет ему отдельную исходящую сеть для SMTP.

Для собственной отправки на том же VPS используется [SMTP-контейнер](deploy/mail/README.md)
с Postfix, авторизацией, TLS и DKIM. Его Compose-файл добавляется после
`deploy/ops/compose.yml`: приложение подключается к SMTP по внутренней сети,
а только почтовый контейнер получает исходящий доступ. SMTP-порты не публикуются.

Проверка подключения, TLS и авторизации без отправки письма:

```bash
npm run mail:check
```

Перед обновлением существующего сервиса:

1. Подготовьте образ и проверьте SMTP с новыми настройками.
2. Создайте [полную резервную копию](docs/backup-and-archives.md), сохранив прежний образ.
3. Остановите writers `app` и `collaboration`, примените миграцию и запустите оба
   сервиса на одной новой версии. Не оставляйте старый сервер совместной работы
   рядом с новым приложением. Штатный контейнер `migrate` также должен использовать
   новый образ и успешно завершиться: его состояние проверяется при возобновлении
   сервисов после резервного копирования.
4. Подтвердите получение письма и вход на контрольном аккаунте. Проверьте
   существующую доску и гостевое приглашение.

Миграция сохраняет аккаунты и доски, оставляет прежним владельцам их места
и не отмечает неподтверждённые адреса как подтверждённые. До подтверждения старая
сессия позволяет подтвердить почту или выйти. При нехватке мест во время активации
потребуется новый код после появления места. Без рабочего SMTP вход
неподтверждённых владельцев завершить невозможно.

На доске откройте «Поделиться», выберите просмотр или редактирование и создайте приглашение. Секрет находится во fragment ссылки; в БД хранится только его hash. В этом же окне можно отозвать ссылку или изменить права конкретного участника.

«Действия с доской» содержит архив владельца; кнопка PDF доступна также редакторам и зрителям. Для печати выделите объекты либо создайте именованные фреймы, задайте порядок и проверьте предпросмотр. Подробности и ограничения: [PDF](export-worker/README.md), [архивы и полная резервная копия](docs/backup-and-archives.md).

## Локальная разработка

Нужны Node.js 22.12+ и отдельная PostgreSQL 18. Создайте пустую БД и скопируйте [config/development.example](config/development.example) в `.env.local`. Укажите свой `DATABASE_URL` и сгенерируйте случайный `BETTER_AUTH_SECRET` длиной не менее 32 символов.

```bash
npm ci
npm run db:migrate
npm run dev
```

Во втором терминале:

```bash
npm run collaboration:dev
```

Интерфейс доступен на [localhost:3000](http://localhost:3000), WebSocket — на порту 1234. `.env.local` читается локальными командами; контейнеры получают переменные через Compose. Значения окружения и данные из `data/` и `temp/` не коммитятся.

Для локального PDF дополнительно установите Chromium через `npx playwright install chromium` и запустите `npm run export-worker` в третьем терминале. Нужен независимый случайный `PDF_WORKER_TOKEN`, одинаковый у приложения и worker; особенности Windows приведены в [инструкции worker](export-worker/README.md).

Публичный адрес WebSocket задаёт серверная переменная `COLLABORATION_PUBLIC_URL`: она читается во время запуска, поэтому один образ можно использовать с разными доменами. В прежнем `.env` переименуйте `NEXT_PUBLIC_COLLABORATION_URL` в `COLLABORATION_PUBLIC_URL`. Сам сервер пока принимает старое имя для совместимости; Compose и примеры используют новое.

## Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm audit --omit=dev
```

`npm test` выполняет проверки без обязательной БД. Чтобы включить настоящие PostgreSQL, cookies, HTTP и WebSocket проверки:

```bash
npm run test:integration
```

Перед запуском задайте `RIMO_TEST_DATABASE_URL` с DSN отдельной тестовой БД в `.env.local` или окружении. Без этого параметра команда завершится до запуска Vitest; `DATABASE_URL` не используется как резервный адрес. Проверки создают собственные временные записи и схемы; не используйте производственную БД для тестов. CI явно задаёт адрес своей тестовой БД и включает PostgreSQL и Chromium. Отдельные Docker backup/resource проверки запускаются по явным флагам из соответствующих инструкций.

Аварийные проверки запускают настоящие процессы, дожидаются подтверждения записи, завершают процесс без shutdown hooks и проверяют восстановление снимка и удалений. Проверяются также viewer-запись напрямую через WebSocket, отзыв доступа, ошибочная и зависшая БД, ограничения очереди и единственный writer.

## Архитектура

```text
app/                     страницы и HTTP API Next.js
components/              существующий интерфейс и диалоги
lib/board/               модель доски, проверка данных и геометрия
lib/collaboration/       Yjs-клиент, presence, история и состояние сохранения
server/                  PostgreSQL, аккаунты, ACL, приглашения и файлы
collaboration-server/    долгоживущий Hocuspocus-процесс и сохранение снимков
server/migrations/       последовательные SQL-миграции с проверкой checksum
server/exports/          фиксированные снимки и связь с PDF worker
export-worker/           проверенный HTML/SVG, локальные шрифты и Chromium
config/                  Caddy и примеры окружения
plan/                    требования, решения и результаты проверок
```

Права доступа хранятся вне совместного документа. Документ содержит версию схемы, карту слоёв с отдельными полями, XML-фрагменты rich text и именованные фреймы с порядком страниц. Изображения представлены стабильными assetId; временные `blob:` URL и base64 в общий документ не записываются.

На одну БД и схему запускается **ровно один процесс совместной работы**. PostgreSQL advisory lock блокирует случайный второй запуск. Детали протокола и действующие защитные ограничения описаны в [collaboration-server/README.md](collaboration-server/README.md). Эти ограничения ещё не являются измеренной вместимостью: профиль больших досок проверяется отдельно.

Бинарное состояние одной доски сейчас ограничено **5 МиБ**, включая историю Yjs,
при общем пределе 500 МиБ. Это более узкий пилотный предел, чем предложенные
в плане 20 МиБ: повышение требует повторной проверки памяти, открытия и записи.
При отказе по квоте вкладка сохраняет локальный черновик и предлагает открыть
сохранённую версию отдельно, чтобы владелец мог выгрузить архив.

Архивы и согласованная копия БД/файлов проверяются восстановлением в новое окружение. Внешнее зашифрованное хранилище и ежедневное расписание настраиваются оператором: без реального репозитория внешняя копия не считается готовой. Подключение облачных сервисов для самой доски не требуется.

Для проверки квот, свободного места и безопасной уборки старых физических orphan-файлов есть [операторская инструкция](docs/operations.md). Уборка по умолчанию только показывает кандидатов; записи assets и используемые файлы сохраняются.

Проверенные версии, измерения и оставшиеся условия выпуска записаны в [протоколе приёмки](plan/verification-report-2026-10-27.md). Для повторения доступны [браузерные сценарии](e2e/README.md), [нагрузочный профиль](docs/performance.md) и [сетевая проверка двух браузеров](docs/network-testing.md).

Понятный обзор готовых возможностей с настоящими снимками интерфейса:
[отчёт владельцу, 8 страниц PDF](plan/progress-report-2026-10-27/Rimo-progress-2026-10-27.pdf).

Правовые проекты для РФ, карта данных и условия внешнего пилота находятся в
[docs/legal](docs/legal/README.md); вопросы владельцу собраны отдельно.
Это внутренние проекты с незаполненными реквизитами и решениями о хранении,
а не опубликованные условия сервиса.

## Обновление

Соберите новую версию и запустите стек:

```bash
docker compose up --build -d --wait
```

Миграции применяются отдельным процессом до старта приложения. Уже применённые SQL-файлы не редактируются. Команда `docker compose down` сохраняет именованные тома; параметр `--volumes` удаляет данные и не используется при обычном обновлении.
