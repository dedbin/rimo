# PDF по областям доски

PDF использует собственное HTML/SVG-представление проверенной модели доски. Текст печатается текстом, фигуры и штрихи — вектором, изображения — сохранёнными WebP. Русские шрифты Noto Sans, Noto Serif, Noto Sans Mono и шрифты KaTeX загружаются из установленных пакетов, без CDN. Полотно и PDF используют общий whitelist гарнитур и одинаковое преобразование прежних названий; code всегда использует Noto Sans Mono. Произвольный HTML, внешние изображения и внешние запросы запрещены. Переполнение текста и формул проверяется в Chromium.

## Действия пользователя

1. Выделить объекты или создать именованный фрейм по выделению/координатам.
2. Выбрать фреймы, порядок, A4/A3/Letter и ориентацию страниц.
3. Дождаться сохранения доски и создать предпросмотр.
4. Проверить все страницы. При мелком тексте, пересечении границы фрейма или переполнении текста/формулы требуется явное подтверждение предупреждений.
5. Скачать PDF. Пока открыта доска, можно продолжать редактирование: готовый предпросмотр и PDF сохраняют одну указанную ревизию.

Границы и порядок задаются человеком; автоматической смысловой перевёрстки нет. Перемещение выбранных фреймов в списке сохраняет полный порядок `frameIds` в Yjs, поэтому архив переносит его вместе с фреймами.

## Фиксированный снимок и API

`POST /api/boards/:boardId/pdf/preview` принимает `minimumRevision` и до 20 описаний страниц:

```json
{
  "minimumRevision": 42,
  "pages": [{
    "source": { "type": "frame", "frameId": "lesson" },
    "format": "A4",
    "orientation": "portrait"
  }]
}
```

Для выделения `source` имеет вид `{ "type": "selection", "layerIds": ["object-id"] }`. Формат и ориентация задаются для каждой страницы в API; диалог применяет общую настройку ко всем выбранным страницам.

Сервер один раз читает `board_documents.state/revision/saved_at`, валидирует schema 2 и материализует только выбранные объекты. Изображения берутся исключительно из записей assets этой доски, сверяются по размеру и SHA-256 и копируются в снимок. Worker получает модель и WebP, без доступа к базе и авторизации пользователей. `/inspect` проверяет реальные размеры текстов и формул тем же Chromium и теми же ресурсами, которыми затем печатается PDF.

Ответ содержит случайный `token`, точную `revision`, срок действия и предупреждения. `GET /api/boards/:boardId/pdf/preview/:token?page=0` показывает страницу в sandbox iframe с CSP. `POST /api/boards/:boardId/pdf` принимает `{ "token": "...", "acceptWarnings": true }` и печатает этот снимок, без повторного чтения живой доски. `DELETE /api/boards/:boardId/pdf/preview/:token` удаляет предпросмотр.

Владелец, editor и viewer могут экспортировать доступную доску. Каждый запрос повторно проверяет сессию и текущий ACL; token привязан к пользователю и доске, а ревизия находится в неизменяемом снимке. После отзыва доступа прежний token не даёт читать или скачивать результат.

Снимки находятся в памяти одного процесса Next.js. Они живут пять минут и автоматически удаляются таймером. Перезапуск приложения сбрасывает предпросмотры; пользователь создаёт их заново. Очередь намеренно недолговечная, без PostgreSQL/Redis: повторная отправка возможна с того же снимка, пока действует token.

## Ограничения

| Ресурс | Предел |
|---|---|
| Страницы | 20 |
| Уникальные объекты в PDF | 3000 |
| Изображения | 100, суммарно 16 МиБ и 40 млн пикселей |
| JSON задания / готовый PDF | 28 МиБ / 32 МиБ |
| Работа по всем страницам с учётом повторов | 20 000 объектов, 500 000 точек штрихов, 8 МиБ исходной модели |
| Сгенерированный HTML | 48 МиБ; изображение встраивается один раз через SVG defs |
| Подготовка снимков в приложении | 2 одновременно |
| Отправки в worker из приложения | 3 одновременно, до сериализации тела |
| Печать и inspect в worker | 1 активное задание + 2 ожидающих |
| Время задания worker | 30 секунд, включая ожидание и чтение тела |
| Хранение предпросмотров | 4 суммарно, 2 на пользователя, 64 МиБ, TTL 5 минут |

Переполнение очереди возвращает 429 до запуска Chromium. Таймаут отвечает ошибкой и завершает дерево процессов отдельного браузера. Следующее задание не начинает печать до очистки предыдущего. Ограничения памяти и числа процессов дополнительно применяет контейнер. Предупреждение о мелком тексте появляется при размере менее 9 pt на бумаге.

## Запуск

Образ: `export-worker/Dockerfile`, Playwright 1.64.1, digest закреплён. Команда `node --import=tsx export-worker/index.ts`, порт 3100, health endpoint `/healthz`. Пользователь контейнера — `pwuser`, Chromium sandbox включён по умолчанию. Compose предоставляет отдельную внутреннюю сеть только для приложения и worker, read-only filesystem, tmpfs, seccomp и предел памяти; база и её секреты worker не передаются.

Worker использует только `PDF_WORKER_TOKEN` (случайный, от 32 символов), `PDF_WORKER_HOST`, `PDF_WORKER_PORT` и при необходимости путь к установленным браузерам Playwright. Приложению нужны тот же `PDF_WORKER_TOKEN` и `PDF_WORKER_URL`, например `http://export-worker:3100`. Секреты задаются окружением, в image их нет.

`config/chromium-seccomp.json` основан на [профиле Playwright 1.64.1](https://github.com/microsoft/playwright/blob/v1.64.1/utils/docker/seccomp_profile.json). При `cap_drop: ALL` дополнительно разрешён syscall `chroot`: Chromium использует его внутри собственного user namespace для [изоляции пустым каталогом](https://chromium.googlesource.com/chromium/src/sandbox/+/refs/heads/main/linux/services/credentials.cc). Системная capability контейнеру не выдаётся; worker остаётся непривилегированным. Профиль проверен настоящей печатью с включённым Chromium sandbox.

Для локальной проверки в Windows, где установлен полный Chromium вместо headless shell:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = "$PWD\temp\playwright-browsers"
$env:PDF_WORKER_BROWSER_CHANNEL = "chromium"
$env:PDF_CHROMIUM_SANDBOX = "false"
$env:RIMO_PDF_BROWSER_TEST = "1"
node --env-file-if-exists=.env.local scripts/test-integration.mjs __tests__/pdf-service.integration.test.ts __tests__/pdf-worker.integration.test.ts
```

`PDF_CHROMIUM_SANDBOX=false` здесь относится к локальному тесту Windows; контейнер Linux проверяется с включённым sandbox. Worker не следует публиковать наружу или снабжать DB/auth secrets.

## Проверка результата

Обычные unit tests проверяют schema boundary, экранирование, порядок/геометрию страниц, лимиты очереди, отмену, TTL и память. Browser integration включается через `RIMO_PDF_BROWSER_TEST=1`; он создаёт в `temp/pdf-acceptance/` контрольные 20 страниц с русским текстом, формулами, фигурами, штрихом и изображением. Service integration использует отдельную случайную схему БД и проверяет фиксацию ревизии, происхождение assets и отзыв доступа.

Дополнительная проверка двумя независимыми extractor:

```sh
python __tests__/pdf-readability.py temp/pdf-acceptance/rimo-control-20-pages.pdf
pdftoppm -f 1 -singlefile -scale-to 1200 -png temp/pdf-acceptance/rimo-control-20-pages.pdf temp/pdf-acceptance/page-01
```

Для первой команды нужны `pypdf` и `pdfplumber`. Она проверяет порядок, размеры листов и целые русские фразы на всех страницах; pdfminer проверяет точное совпадение без склеивания букв. Полученные PNG нужно просмотреть: извлечение текста не доказывает отсутствие обрезки формул или визуальных дефектов. Контроль на машине разработчика не заменяет замер VPS и параллельного урока.
