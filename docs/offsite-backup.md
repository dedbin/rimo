# Передача полной копии через restic

Обвязка передаёт завершённый каталог `backup-service.mjs` в уже настроенный репозиторий restic. Она не останавливает сервисы и не создаёт локальную копию. Оператор отдельно устанавливает restic 0.19.1+, настраивает backend, создаёт репозиторий и хранит пароль с ограниченным доступом. Проверка реального восстановления остаётся отдельной обязательной приёмкой.

## Настройка оператора

Укажите ровно одну переменную: `RESTIC_REPOSITORY` либо `RESTIC_REPOSITORY_FILE`. Пароль передавайте только через `RESTIC_PASSWORD_FILE`. Обвязка отклоняет `RESTIC_PASSWORD` и `RESTIC_PASSWORD_COMMAND`; файлы конфигурации и паролей должны находиться вне каталога копии и Git. Доступ к ним ограничивается правами ОС. Учётные данные S3/SFTP/другого backend задаются штатным окружением restic.

Пример PowerShell, значения путей заменяет оператор:

```powershell
$env:RESTIC_REPOSITORY_FILE = 'C:\private\rimo-restic.repository'
$env:RESTIC_PASSWORD_FILE = 'C:\private\rimo-restic.password'
node scripts/restic-backup.mjs --input data/backups/manual-001 --project rimo
```

Для Unix используются те же имена переменных и команда Node. Исполняемый файл `restic` должен быть доступен в `PATH`. Репозиторий предварительно создан оператором: обвязка никогда не выполняет `init`, `unlock`, `forget`, `prune`, удаление или автоматическую настройку расписания. Произвольные дополнительные аргументы restic не принимаются.

## Передача и подтверждение

Каталог должен содержать ровно `manifest.json`, `database.dump`, `assets.tar`: обычные файлы без ссылок. Staging-каталоги отклоняются. Существующий helper проверяет формат, размеры и SHA-256, а `sourceProject` обязан совпасть с `--project`. Завершённую копию нельзя изменять во время передачи. После snapshot файлы и manifest проверяются повторно.

Запускаются только:

1. `restic backup --json --host <текущий-hostname> --tag rimo-service:<project> --tag rimo-source:<UTC-время-данных> -- <абсолютный-каталог>`.
2. `restic snapshots --json --host <тот-же-hostname> --tag <та-же-метка> <новый-полный-ID>`.
3. `restic check --json --read-data`.

Принимается только полный `snapshot_id` из единственного завершающего summary, затем ровно один snapshot с тем же ID, hostname, двумя точными метками и исходным путём. Его время должно соответствовать интервалу передачи с допуском 60 секунд. Вторая метка сохраняет `manifest.capturedAt`: время после остановки writers перед dump. Для прежних manifest без этого поля используется `createdAt`; оно обозначало завершение локальной копии. Повторная передача того же dump сохраняет возраст исходных данных.

Любой ненулевой, неизвестный или отсутствующий exit code restic означает отказ, включая частичный backup с кодом 3. `check --read-data` проверяет весь репозиторий; принимается только exit 0 и явное `num_errors: 0`. Передача в общий большой репозиторий может быть длительной.

Успех выводится одной безопасной JSON-строкой:

```json
{"complete":true,"mode":"backup","snapshotID":"<64 hex>","createdAt":"<UTC передачи>","sourceCreatedAt":"<UTC данных>","status":"fresh","ageSeconds":30,"encrypted":true,"dataVerified":true,"offsiteVerified":false}
```

Адрес репозитория, пути, hostname и необработанные stdout/stderr restic не выводятся. При ошибке возвращаются `complete=false`, безопасные `stage`/`errorCode`, `dataVerified=false`. Если ID уже получен, поле `knownSnapshotId` сохраняется: ошибка последующей проверки не означает, что snapshot отсутствует. Snapshot не удаляется автоматически.

Команды backup/check ограничены 30 минутами каждая, metadata — 60 секундами; общий stdout/stderr одной команды — 8 МиБ. SIGINT/SIGTERM отменяют текущий дочерний процесс с последующим принудительным завершением при необходимости. Оставшийся lock требует ручного разбора оператором; автоматического unlock нет.

`encrypted=true` означает успешную работу с шифрованным форматом restic. **`offsiteVerified` всегда false**: доступность локального или сетевого репозитория не доказывает его независимость от исходного сервера. Для внешней копии оператор должен выбрать отдельное хранилище, проверить доступ и провести восстановление в независимом окружении. Пароль и доступ к backend нужны и при восстановлении.

## Проверка возраста

```powershell
node scripts/restic-backup.mjs --check-age --project rimo
```

Локальный каталог не нужен и `--input` в этом режиме запрещён. Проверяются metadata только с точной меткой проекта и hostname текущей машины. Это позволяет менять ежедневные каталоги и удалять старые локальные копии. Другой hostname после переезда требует отдельного решения оператора, а не автоматического признания чужих snapshot свежими.

Из подходящих snapshot выбираются самые свежие **исходные данные**, а возраст считается по `rimo-source`, не по дате передачи. Отсутствующая, неправильная или неоднозначная метка не признаётся свежей копией и даёт ошибку. Данные свежи до 24 часов включительно. Время более чем на 60 секунд в будущем даёт `status="future"`; меньший допуск отражается отрицательным `ageSeconds`. Часы оператора должны быть корректны. Проверка возраста не читает данные репозитория повторно: `dataVerified=false` в её результате.

Коды обвязки:

| Код | Значение |
| --- | --- |
| 0 | Передача и полная проверка успешны либо age-check нашёл свежий snapshot |
| 1 | Snapshot отсутствует либо исходные данные старше 24 часов или за допуском в будущем; завершённая передача старых данных также возвращает 1 |
| 2 | Ошибка аргументов, локальной копии, доступа, процесса или проверки |

## Ежедневная последовательность на Linux

Каждый запуск сначала создаёт **новую** согласованную локальную копию. Один и тот
же `--output` не переиспользуется: backup-service отказывается перезаписывать
существующий каталог. Пример отдельного `/srv/rimo/backup-daily.sh`:

```sh
#!/bin/sh
set -eu
umask 077
mkdir -p /srv/rimo-backups
exec 9>/srv/rimo-backups/daily.lock
flock -n 9
run_dir=$(mktemp -d /srv/rimo-backups/run.XXXXXXXX)
cd /srv/rimo
node scripts/backup-service.mjs --project rimo --env-file .env --compose-file docker-compose.yml --output "$run_dir/complete"
node scripts/restic-backup.mjs --project rimo --input "$run_dir/complete"
```

`flock` и `mktemp` — штатные утилиты Linux. Каталог копий и файлы окружения
доступны только доверенному оператору. Имя проекта, пути и исполняемый Node
оператор подставляет при установке. Локальная копия кратко останавливает app и
collaboration для согласованности; ежедневное окно выбирается с учётом занятий.
При отказе передачи локальные файлы сохраняются для повторной попытки.

Пример systemd service, `rimo-backup.service`:

```ini
[Service]
Type=oneshot
WorkingDirectory=/srv/rimo
EnvironmentFile=/etc/rimo/restic.env
ExecStart=/bin/sh /srv/rimo/backup-daily.sh
TimeoutStartSec=75min
```

Его timer, `rimo-backup.timer`:

```ini
[Timer]
OnCalendar=*-*-* 04:00:00 UTC
Persistent=true
Unit=rimo-backup.service

[Install]
WantedBy=timers.target
```

Оператор отдельно включает timer, проверяет фактический первый запуск и
настраивает обработку ненулевого кода. Проверку `--check-age` запускают независимо
хотя бы раз в час: успешный запуск таймера не доказывает свежесть данных.
Локальные каталоги и restic snapshots накапливаются; политику хранения и очистку
настраивают после проверенного восстановления. Автоматического удаления здесь
нет. На этом компьютере расписание не устанавливается; без реального внешнего
назначения ежедневная внешняя копия ещё не включена.

Протокол JSON и коды restic: [официальная документация scripting](https://restic.readthedocs.io/en/stable/075_scripting.html). Восстановление из restic: [официальная инструкция](https://restic.readthedocs.io/en/stable/050_restore.html), затем существующий `restore-service.mjs` для полученного каталога полной копии.
