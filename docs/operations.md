# Операторские команды

Команды выполняются вручную из каталога проекта. Они загружают `.env.local`, затем `.env`, используют обычное подключение PostgreSQL и завершают пул перед выходом. Значения переменных окружения не нужно передавать в аргументах команд.

## Состояние сервиса

```sh
node --import=tsx scripts/service-status.ts
```

После обновления образа приложения:

```sh
docker compose exec -T app node --import=tsx scripts/service-status.ts
```

Команда возвращает один JSON-объект `version: 1`. В нём нет содержимого досок, идентификаторов пользователей, имён, почты, cookies, путей хранилища или строк подключения.

| Поле | Значение |
| --- | --- |
| `checkedAt` | Время проверки в UTC |
| `status` | `healthy`, `warning` или `critical` |
| `reasonCodes` | Причины состояния без текстов внутренних ошибок |
| `database.reachable` | Удалось выполнить настоящий SQL-запрос и получить агрегаты сервиса |
| `usage` | Количество владельцев, досок, документов и записей изображений; байты документов и изображений; максимальное использование одним владельцем или доской |
| `quotas` | Действующие значения квот из конфигурации |
| `storage` | Доступность чтения и записи, свободные и общие байты тома, количество и суммарная длина обычных файлов верхнего уровня, число пропущенных каталогов и ссылок |

Владельцами считаются только аккаунты с `isAnonymous = false`. В максимумах по владельцу или доске публикуется только число, без указания аккаунта или доски. Байты изображений в `usage` берутся из PostgreSQL; `storage.fileBytes` — сумма длин обычных файлов верхнего уровня, включая физические файлы без записи в БД. Это разные показатели. `fileBytes` не оценивает сжатие и занятые блоки файловой системы.

Коды завершения:

| Код | Состояние |
| --- | --- |
| `0` | Проверки прошли, пороги не достигнуты |
| `1` | Предупреждение |
| `2` | Критическое состояние или проверка недоступна |

Предупреждение появляется при использовании любой квоты от 80%. Полные лимиты владельцев, досок и изображений также дают `warning` с кодом `LIMIT_REACHED`: они ограничивают создание аккаунтов, досок или загрузку файлов, а существующие занятия продолжаются. Например, шесть владельцев при лимите шесть — заполненный пилот с предупреждением. Общая квота документов на 100% даёт `critical`, поскольку рост сохранённых документов может быть заблокирован.

Место на томе загрузок оценивается отдельно: предупреждение ниже 2 GiB **или** 10%, критическое состояние ниже 256 MiB **или** 2%. Недоступность БД, каталога, чтения или записи также даёт `critical`. Например, `GLOBAL_ASSETS_LIMIT_NEAR` означает приближение общей квоты изображений, `STORAGE_SPACE_LOW` — недостаточный запас свободного места. Если SQL-проверка или проверка каталога не выполнена, соответствующий блок содержит `null`, а `reasonCodes` указывает причину.

Команда не создаёт отсутствующий каталог загрузок и не запускает миграции. Она оценивает состояние с правами текущего процесса; в Docker используйте пользователя приложения через `exec app`.

## Проверка физических файлов без ссылки в БД

По умолчанию команда только показывает кандидатов:

```sh
node --import=tsx scripts/prune-orphan-assets.ts
docker compose exec -T app node --import=tsx scripts/prune-orphan-assets.ts
```

Удаление включается явно:

```sh
node --import=tsx scripts/prune-orphan-assets.ts --apply
docker compose exec -T app node --import=tsx scripts/prune-orphan-assets.ts --apply
```

В JSON указаны режим, кандидаты с UUID-именами и размером, результат для каждого кандидата, число удалений и причины остановки. Режим `dry-run` помечает кандидатов `would-remove` и ничего не удаляет. `apply` помечает фактически удалённые файлы `removed`. За один запуск обрабатывается не более 1000 кандидатов; `limited: true` означает, что после просмотра результата команду можно повторить. Список записей БД проверяется небольшими порциями, без загрузки всех ключей в память.

Кандидат должен одновременно удовлетворять всем условиям:

- Находится непосредственно в настроенном абсолютном `ASSET_STORAGE_PATH`.
- Имеет имя UUID с расширением `.webp`, `.png`, `.jpeg` или `.gif`.
- Является обычным файлом с единственной жёсткой ссылкой.
- И время изменения содержимого (`mtime`), и время изменения метаданных (`ctime`) старше либо равны 24 часам. Поэтому перенос или изменение прав старого файла может отложить его уборку ещё на сутки.
- Его имя отсутствует среди `assets.storage_key`.

Каталоги, симлинки, junctions, дополнительные жёсткие ссылки, незнакомые имена, новые или изменившиеся файлы сохраняются. Уборщик не обходит вложенные каталоги и не печатает их имена. Настроенный каталог также не может быть корнем тома или содержать симлинк в пути.

Перед каждым удалением команда берёт короткую блокировку `assets` в режиме `SHARE`, повторно проверяет отсутствие ссылки и проверяет исходный каталог, устройство, inode, размер, `mtime`, `ctime` и число ссылок файла. Между файлами блокировка освобождается. Ожидание блокировки ограничено тремя секундами; ошибка прерывает уборку. Если PostgreSQL недоступен при запуске, обход файлов даже не начинается. При сбое в ходе удаления оставшиеся файлы сохраняются, а `removedCount` показывает уже выполненные удаления.

Уборщик не удаляет записи `assets`, другие строки БД или аккаунты. Файл с записью `assets` сохраняется даже после удаления слоя: история undo и сохранённые документы могут продолжать ссылаться на него. Автоматического таймера уборки нет.

Каталог загрузок должен оставаться доступным для записи только сервису и доверенному оператору. Во время восстановления полного сервиса выполняйте последовательность из [инструкции резервного копирования](backup-and-archives.md); одновременно запускать восстановление и ручную уборку не требуется.

## Журналы контейнеров

Compose использует встроенный Docker `local` driver с ротацией: до трёх файлов
по 10 МиБ на сервис. Настройка применяется при создании контейнеров; обычное
обновление через `docker compose up -d --wait` пересоздаёт контейнеры с изменённой
конфигурацией. Просмотр: `docker compose logs --since 1h --tail 200 app collaboration`.
Файлы драйвера обслуживает Docker; читайте их через `docker logs`/Compose.
Описание опций — в [документации Docker](https://docs.docker.com/engine/logging/drivers/local/).

Загрузка и перенос изображений на Linux сбрасывают байты файла и каталог
хранилища через `fsync` перед записью метаданных в БД. Импорт архива выполняет тот
же барьер для опубликованных изображений до COMMIT. В Windows development
сбрасывается файл; синхронизация каталога через Node возвращает `EPERM` и не
используется. Поведение накопителя и файловой системы остаётся частью
эксплуатационной конфигурации; это не проверка потери питания.

## Проверка изменений

Событие `collaboration_access_check_failed` в журнале collaboration содержит
только `kind` и `elapsedMs`. `timeout` означает истечение трёхсекундного
ожидания проверки, включая очередь запросов и задержки event loop;
`dependency-error` — отказ внутренней операции; `denied` — отсутствие действующей
сессии или доступа; `editor-limit` — повышение до редактора при заполненном лимите
записывающих соединений. Идентификаторы, cookies и текст SQL не выводятся.
Сервис прекращает доступ при неуспешной проверке; это событие помогает отличать
отзыв прав от перегрузки или ошибки БД. Обычная разрешённая смена роли не создаёт
такое событие.

```sh
node --env-file-if-exists=.env.local scripts/test-integration.mjs __tests__/operations.integration.test.ts
npx vitest run __tests__/operations-status.test.ts
```

Интеграционные тесты используют отдельную случайную схему PostgreSQL и временный каталог. Они проверяют реальное чтение агрегатов, dry-run, удаление старого orphan, сохранение свежих и referenced файлов, ссылок и изменённого файла, повторную проверку новой записи БД, отказ подключения и тайм-аут блокировки. Рабочие строки сервиса и рабочее хранилище не изменяются.
