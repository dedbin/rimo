# Архив доски и резервная копия сервиса

## Архив отдельной доски

Владелец скачивает `.rimo`: обычный ZIP с `manifest.json`, полным `board.yjs`, переносимым `board.json` и изображениями `assets/<id>.webp`. Совместный документ является основным представлением. Его бинарное состояние сохраняет полную поддерживаемую схему Yjs, включая текстовые XML fragments удалённых объектов для undo. JSON имеет отдельную версию: версия 1 описывает прежнюю модель, версия 2 добавляет проверенное `richText` активных текстов и стикеров с форматированием и исходником LaTeX. После расширения схемы проверки и roundtrip повторяются.

Экспорт берёт последнее подтверждённое состояние PostgreSQL и фиксирует его revision. Во время создания временного ZIP доска удерживается `FOR SHARE`, чтобы удаление файлов не испортило копию. Совместное редактирование продолжается; новые изменения не попадают в уже зафиксированный снимок. Блокировка строки снимается до передачи файла браузеру.

Восстановление создаёт новую доску текущего владельца. Все изображения получают новые UUID, а ссылки в типизированных слоях заменяются. Байты WebP сохраняются точно после проверки SHA-256, фактического формата, размеров и полного декодирования. Аккаунты, сессии, участники и приглашения из архива не импортируются. Исходная доска не меняется.

ZIP читается последовательно, с проверкой имён, повторных записей, размеров и хешей. Произвольное извлечение путей не используется; распакованные файлы получают сгенерированные имена в закрытом временном каталоге. Ссылки, шифрованные и посторонние файлы отвергаются. JSON должен соответствовать совместному документу.

Архив прежней схемы сначала проверяется вместе с исходным JSON версии 1, затем обычный текст мигрирует в XML fragments и проходит строгую проверку схемы 2. Неизвестные shared roots и будущие версии явно отклоняются. Сохранённую доску прежней схемы можно экспортировать до первого открытия редактора после обновления.

Одна операция архива на БД/схему; занятый обработчик отвечает `429`. Загрузка потоком ограничена 256 МиБ и 60 секундами, вся операция — двумя минутами. Распакованное содержимое — до 256 МиБ, описание — 4 МиБ, JSON — 32 МиБ, объектов изображений — до 10 000. Дополнительно действуют более строгие лимиты документа, отдельного изображения, владельца и всего сервиса. Недостаток места, ошибка валидации или квоты не оставляет частично восстановленную доску.

## Полная копия PostgreSQL и файлов

Нужны Node.js 22+ и Docker Compose. Команды работают через `child_process.spawn` без PowerShell-перенаправлений бинарных данных. Явно выбранный env-файл имеет приоритет над переменными другого окружения, загруженного вызывающим Node-процессом.

```text
node scripts/backup-service.mjs --project rimo --env-file .env --output data/backups/manual-001
node scripts/restore-service.mjs --project rimo-restored --env-file .env.restore --input data/backups/manual-001
```

Для согласованной копии команда на короткое время останавливает работающие `app` и `collaboration` с grace period 30 секунд. Затем делает PostgreSQL custom dump и tar вложений; приватные временные архивы исключаются. Манифест содержит версии и SHA-256 обоих файлов. Остановленные командой процессы запускаются в `finally`, включая случай ошибки или обычного `SIGINT`/`SIGTERM`. Прерывание ждёт окончания grace period и не отменяет возобновление сервисов. Передача во внешнее хранилище выполняется после возобновления сервиса.

Одновременные backup/restore одного проекта отклоняются до остановки сервисов. Резервация использует уникальное имя незапускаемого Docker-контейнера `rimo-backup-lock-<project>`, без томов и секретов. После завершения удаляется только созданный этим вызовом контейнер. После аварии компьютера или принудительного уничтожения Node-процесса резервация может остаться: оператор проверяет отсутствие выполняющейся копии и состояние сервисов, возобновляет остановленные процессы, затем явно удаляет `docker rm rimo-backup-lock-<project>`. Автоматического удаления чужой резервации нет.

Восстановление разрешено только в новый Compose-проект с новыми, собственными томами PostgreSQL и вложений. Существующие контейнеры и тома не перезаписываются. Сначала проверяются хеши; PostgreSQL восстанавливается одной транзакцией с остановкой на первой ошибке, затем файлы и сервис. Требуется тот же major PostgreSQL и совместимая версия приложения. Env-файл нового проекта должен задавать отдельные публичные порты и адрес; `DATABASE_URL` обязан указывать на его сервис `db`.

Проверка восстановления допускает только обычные локальные тома `<project>_postgres-data` и `<project>_assets` без `external`, других драйверов и `driver_opts`. Поэтому новое имя тома нельзя использовать как ссылку на прежний каталог через bind/NFS. Дополнительные mount поверх, внутри или над каталогом данных, а также `tmpfs` и `volumes_from` у сервисов данных отклоняются до запуска восстановления. Если заданы `PGDATA` или `POSTGRES_INITDB_WALDIR`, их каталоги должны находиться внутри тома PostgreSQL. Пользовательские `POSTGRES_INITDB_ARGS` не поддерживаются восстановлением, поскольку могут перенаправить WAL в обход этих настроек.

Полная копия включает учётные записи и сессии, поэтому хранится с доступом только владельцу и передаётся в зашифрованное внешнее хранилище. На Unix скрипт создаёт каталоги с `0700`, файлы с `0600`; на Windows доступ определяется наследуемым ACL выбранного родительского каталога. SQL dump восстанавливает только оператор из собственной доверенной копии; он не принимается публичным HTTP API. `.rimo` имеет другой формат и собственную проверку данных.

## Проверка восстановления

`__tests__/archive.integration.test.ts` работает с тестовым PostgreSQL, имеющим разрешение создавать временную БД. Помимо HTTP/ACL/ZIP/квот он экспортирует архив и восстанавливает его отдельным Node-процессом в пустую БД с новым владельцем и каталогом файлов. Проверяются форматирование, исходник LaTeX, orphan fragments, порядок слоёв и точный SHA-256 изображения; исходные аккаунты и записи для этого не нужны. Собственные временные БД/схема и файлы удаляются после теста. После перехода на текстовую схему 2 этот сценарий и проверки потоков/формата прошли 25 из 25, включая отказ миграции слишком сложного прежнего текста без обрезки или частичной доски.

Для локальной приёмки используется `RIMO_TEST_DOCKER_BACKUP=1` и `vitest run __tests__/backup-compose.integration.test.ts`. Тест сам создаёт два Compose-проекта с новыми томами и удаляет только их. Он сравнивает SHA-256 полного Yjs и изображения, проверяет вход прежнего владельца и выдачу файла по HTTP после восстановления. Отдельно проверяются отказ второго запуска, отказ перезаписи существующего проекта и возобновление обоих сервисов после намеренной ошибки tar и события `SIGINT` во время остановки.

На Windows с Docker Desktop и PostgreSQL 18 проверка 27 октября 2026 года прошла за 53 секунды. Это небольшая контрольная доска с одним изображением; результат не является измерением времени восстановления максимального объёма на VPS. После смены версии приложения/схемы такую проверку повторяют перед доверием новой копии.

## Внешнее хранилище

Для передачи и шифрования используется готовый `restic`. Репозиторий может быть SFTP или S3-совместимым. Пароль задаётся через `RESTIC_PASSWORD_FILE`, адрес — через `RESTIC_REPOSITORY`; файлы паролей и конфигурации не включаются в Git. Обычная последовательность после локальной копии: `restic backup <каталог-копии>`, затем проверка кода завершения и `restic snapshots`. Восстановление: `restic restore <snapshot-id> --target <новый-каталог>`, затем `restore-service.mjs`.

После подключения внешнего репозитория оператор настраивает ежедневный вызов и хранение нужного числа снимков; успешность проверяется по фактическому снимку, а не запуску таймера. До появления внешнего репозитория и его проверки цель «внешняя копия не старше 24 часов» не считается выполненной. Локальный roundtrip подтверждает работу восстановления, но не независимость от потери компьютера/VPS.
