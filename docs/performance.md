# Проверка производительности

Пределы плана A — критерии приёмки: 3000 объектов, 500 видимых, выделение и перенос 500; локальная реакция до 50 мс и p95 кадра до 33 мс на зафиксированном компьютере. Отдельный профиль — час работы 50 соединений, из них 10 редактирующих. Результаты одного компьютера и loopback не доказывают эти цифры на VPS или при RTT 100 мс.

## Воспроизводимые команды

Нужны Node 22.15+, `npm ci`, собранные production app/collaboration и действующий storage state тестового владельца. Harness использует штатные HTTP/WS, не обращается к БД и не требует debug API. Новые аккаунты владельцев не создаются. Состояния входа хранятся в игнорируемом `temp`; отчёты не содержат cookies, приглашений или паролей. Для ошибок сторонних библиотек сохраняются только разрешённые имена операций и коды сети. Playwright Call log с заголовками не сохраняется.

Node provider переносит cookies через [tough-cookie 5.1.2](https://github.com/salesforce/tough-cookie/tree/v5.1.2), закреплённый как прямая dev dependency. Он выбирает их для HTTP(S)-эквивалента полного WS URL с учётом host-only/Domain, границы Path, expiry, Secure и префиксов. Host приложения и WebSocket должен точно совпадать; допустимы пары HTTP→WS и HTTPS→WSS, порты могут различаться. Secure не переносится по WS даже на localhost. Partitioned/CHIPS cookies пропускаются: Node-соединение не имеет контекста top-level partition. Приватные cookie API Playwright не используются.

Быстрая проверка сценария без сервиса и браузера:

```text
node --import=tsx scripts/measure-editor.mjs --self-test
npx vitest run __tests__/performance-harness.test.ts
```

Она проверяет реальную серверную схему и геометрию: 3000 валидных объектов, 500 пересекают viewport, штатное выделение захватывает 500. Также проверяются один экземпляр Yjs, отказ часового запуска без явного разрешения и двухсекундный изолированный WebSocket-сценарий writer/viewer с batch, ping/pong и подтверждением сохранения. Для него не нужны production сервис или БД.

Desktop-замер в PowerShell:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = (Resolve-Path temp/playwright-browsers).Path
node --import=tsx scripts/measure-editor.mjs --storage-state temp/browser-owner-storage.json --label local-production-diagnostic --output temp/performance/editor.json
```

Используется полный Chromium через `channel: chromium`, headless, viewport 1440×1000, deviceScaleFactor 1, ru-RU. Для новой установки браузера: `npx playwright install chromium`. Сборку и версию окружения оператор задаёт `--label`; текущий Git commit, dirty-флаг, Node, Next, ОС, CPU, RAM, Chromium, WebGL renderer и загруженные шрифты записываются автоматически. `--enforce-budgets` возвращает ненулевой exit code при нарушении бюджета. Диагностический запуск не объявляется финальной приёмкой.

Короткая проверка совместного сервиса:

```text
node --import=tsx scripts/load-collaboration.mjs --seconds 30 --rooms 1 --connections 10 --editors 2 --output temp/performance/load-smoke.json --label local-production-diagnostic
```

Часовой профиль запускается только вручную после финальной сборки:

```powershell
$env:RIMO_RUN_LONG_LOAD = '1'
node --import=tsx scripts/load-collaboration.mjs --seconds 3600 --rooms 5 --connections 50 --editors 10 --compose-project rimo --label accepted-image-digest-and-host --output temp/performance/load-hour.json
```

`--compose-project` должен обозначать измеряемый проект: тогда отчёт содержит `docker stats`, image ID и лимиты CPU/RAM его контейнеров. Запрашиваются только эти поля; Docker Config.Env с секретами не читается. Статистика собирается параллельно генератору и не задерживает отправки. Без этого флага память и event loop относятся только к генератору. Имя проекта и label нужно заменить фактическими. `--base-url` выбирает origin app; WebSocket URL берётся из штатного `/api/boards/:id/session`. Cookie передаётся только WebSocket того же хоста с совместимой защищённой схемой.

## Контрольная сцена и жест

Сцена версии 1 создаётся на новой доске: 1500 прямоугольников, 600 эллипсов, 300 путей, 300 изображений и 300 текстов с кириллицей и inline LaTeX. В viewport расположены 250/100/50/50/50; остальные 2500 лежат за его пределами и должны отсекаться. Изображения повторяют одно небольшое реальное WebP-вложение: это контроль рендеринга 300 слоёв, а не загрузки 300 разных файлов. Шрифты и все 50 видимых изображений должны загрузиться и декодироваться до измерения.

Браузер выделяет 500 объектов обычной рамкой и проверяет selection по presence. Затем трижды переносит их на 120×40 за 180 pointermove с паузой 16 мс. В протоколе жеста 2 первый move проходит 4 экранных пикселя вдоль траектории, сразу пересекая штатный порог 3 px; остальные 179 продолжают тот же перенос, последнее событие приходит точно в 120×40. Промежуточного искусственного прогрева нет, первое preview остаётся в метриках. Реальная частота событий записывается: пауза не гарантирует 60 Гц. После каждого жеста проверяются координаты всех 3000 объектов, отсутствие промежуточных изменений координат в CRDT, одна конечная транзакция, подтверждение persisted и возвращение всех 500 одним undo.

`reactionProxyMs` — исходное время от PointerEvent timestamp до следующего rAF после изменения SVG transform. Оно сохраняется целиком, включая первое ещё не отражённое событие до порога жеста. `startup` отдельно записывает первый move→пересечение 3 px, pointerdown→пересечение, первый move→первое preview и пересечение→первое preview. `activeDragReactionProxyMs` отсчитывает реакцию от первого ещё не отражённого move, который пересёк 3 px, и от последующих движений. Это DOM/rAF proxies, включая очередь события, без доказанного показа пикселей compositor. Для новых прогонов критерий 50 мс применяется к active drag, включая первое preview после намерения переноса; raw startup публикуется отдельно. С первым move 4 px оба отсчёта начинаются на одном событии. Старые отчёты и их критерии не переписываются.

Численный trace хранит первые 12 input и первые 8 реакций плюс ограниченное число выбросов; в нём нет DOM-текста или сетевых заголовков. Отдельно сохраняются доступные native Event Timing entries, input delay и processing duration; отсутствие entries не означает нулевую задержку. Непрерывный pointermove не включён в Event Timing по [спецификации W3C](https://www.w3.org/TR/event-timing/#sec-events-exposed).

`frameMs` измеряет промежутки rAF во время жеста и двух заключительных кадров; p95 — nearest rank. В отчёте также есть long tasks, CDP JSHeap/DOMNode counts, protocol types, application bytes и фактический размер снимка Yjs. Эти bytes не включают WebSocket framing/TCP/TLS. Метрики heap не являются полным RSS процесса Chromium.

### Протокол измерения 5

В протоколе 5 `reactionProxyMs`, `activeDragReactionProxyMs` и startup используют `performance.now()` внутри rAF callback после изменения preview. Аргумент rAF — общий timestamp серии callbacks, который может предшествовать mutation и выполнению конкретного callback; это следует из [алгоритма WHATWG](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks). В trace отдельно сохраняются `mutationMs`, фактический `callbackMs` и диагностический `rafTimestampMs`. Кадровый ряд `frameMs` продолжает использовать интервалы rAF timestamps. Пределы 33/50 мс, input timestamps, порог жеста, сценарий и отсутствие прогрева сохранены. Это по-прежнему DOM/rAF proxy без доказательства показа пикселей compositor.

Исторические raw протоколов 3/4 и их критерии сохраняются без переписывания: реакция по rAF timestamp могла занижаться. Ограниченного trace недостаточно для пересчёта всех распределений; для приёмки по исправленному proxy нужен отдельный прогон протокола 5.

## Нагрузочный профиль и его пределы

Для 50/10 создаются пять своих досок: по два writer и восемь viewer соединений. Writer используют текущую сессию владельца; viewer — одну переиспользуемую анонимную сессию с явным приглашением в каждую доску. Это 50 соединений двух учётных записей. Read-only scope каждого viewer проверяется при соединении. Тестовый viewer state по умолчанию — `temp/performance-viewer-storage.json`; `--viewer-storage-state` меняет путь. Если вход истёк или отсутствует, создаётся один anonymous аккаунт и сохраняется приватный state. Аккаунт остаётся для повторных замеров, поскольку его удаление через API сервиса отключено. На Unix новый state создаётся с `0600`, на Windows доступ определяется ACL родительского каталога.

Каждая доска содержит 3000 объектов той же сцены. По умолчанию каждый writer делает две конечные операции в секунду, отправляет cursor presence до 10 раз/с и каждые 30 секунд переносит до 500 своих объектов одной транзакцией. Группы разных writer не пересекаются. Фактические частоты, пропущенные ticks и размеры batch записываются; настройки доступны через `--edit-hz`, `--presence-hz`, `--batch-size`, `--batch-every-seconds`.

Задержка propagation — доставка изменения от Node provider всем остальным Node provider комнаты, без браузерного рендеринга. Проверяется причинное включение операции через Yjs state vector: объединённые обновления не считаются потерей прежних координат. Используется ограниченная по памяти [Node.js HDR histogram](https://nodejs.org/docs/latest-v22.x/api/perf_hooks.html#perf_hookscreatehistogramoptions), точность 3 значащих цифры. Pending delivery и outbound bufferedAmount — измеренные proxies; внутреннюю очередь Hocuspocus этот интерфейс не раскрывает. В конце ждём равенства снимка подтверждению БД у каждого клиента и проверяем сходимость.

Отчёт различает RSS/heap/event loop генератора и Docker CPU/RAM сервиса. Сэмплы снимаются каждые 10 секунд (`--sample-seconds`); histogram не накапливает сырые события. В каждой комнате измеряется round trip WebSocket ping/pong, включая задержку callback генератора. Ошибка, прерывание или недоставленные изменения не превращаются в успех; уже собранные сэмплы сохраняются. В `--network-label` указывается фактическая сеть. Строка «RTT 100 мс» не эмулирует задержку: сеть настраивают отдельно и записывают в протокол.

SIGINT/SIGTERM/SIGHUP сразу устанавливают ненулевой exit code и позволяют выполнить finally-очистку. У Chromium отключена собственная обработка этих сигналов, чтобы Playwright не завершил процесс до удаления тестовой доски и записи отчёта. Финальный статус прерванного сценария — `interrupted`, при ошибке очистки — `cleanup-failed`; handlers остаются до конца записи JSON. Если сигнал пришёл во время атомарной записи, прежний снимок отчёта заменяется ещё раз. Успешный drain и достаточная частота операций не превращают укороченный профиль в полный. Короткий изолированный self-load проверяет SIGINT/SIGTERM с writer/viewer и реальными ACK; адресные тесты проверяют поздние сигналы во время очистки и записи. Это не запуск нагрузки на Rimo или часового профиля.

Функциональная проверка desktop-прерывания сохранена в `temp/performance/editor-interruption-check.json`: настоящий Chromium дошёл до `gesture-1` на своей доске с 3000 объектами, 500 видимыми и 50 декодированными изображениями. В Windows сигнал доставлен через private IPC в зарегистрированный Node SIGINT handler; это проверка handler, а не native SIGTERM. Процесс завершился с кодом 1, отчёт — `interrupted`, ошибки очистки отсутствуют, HTTP-проверка собственной доски после finally вернула 404. Скорость этого запуска не использовалась для приёмки.

## Очистка и интерпретация

Harness создаёт свои доски с новыми UUID и удаляет их через owner API в finally, включая ошибки замера. Существующие доски не используются. Вместе удаляются memberships, invites и вложения этих досок. Их ID записываются в `createdBoards` отчёта сразу после создания: после принудительного уничтожения процесса или компьютера оператор проверяет эти имена и ID и удаляет оставшиеся тестовые доски. Переиспользуемый viewer аккаунт и приватные storage state остаются; общая уборка истёкших гостей и orphan assets — отдельная операторская процедура.

Поле `status: complete` означает завершённый сценарий. Для приёмки нужны бюджеты desktop, отсутствие ошибок и неподтверждённых правок, часовой профиль с анализом памяти и очередей на зафиксированном хосте и отдельная проверка двух настоящих браузеров при RTT 100 мс. До этого DEFAULT_LIMITS остаются защитными настройками; вместимость сервиса ещё не доказана.

## Диагностический CPU profile

`scripts/performance/profile-cpu.mjs` использует встроенный V8 sampling profiler уже запущенного собственного collaboration-контейнера. SIGUSR1 включает inspector только на `127.0.0.1:9229` внутри контейнера; порт не публикуется на хост. Harness отказывается занимать уже работающий inspector. После Profiler.stop, ошибки или прерывания он закрывает свой inspector; отдельный `docker exec` проверяет отказ подключения к 9229. Снимаются CPU-стэки функций, без heap snapshots, payloads и заголовков. Raw `.cpuprofile` и численная сводка могут сохраняться только внутри игнорируемого `temp`.

Для исключения seed/handshake из профиля load harness поддерживает необязательный барьер. Сначала запустить обычный короткий профиль 50/10 с дополнительным `--start-signal temp/performance/cpu-start.signal` и дождаться `load_ready`. Затем во втором терминале:

```text
node scripts/performance/profile-cpu.mjs --compose-project rimo-rework --seconds 35 --start-signal temp/performance/cpu-start.signal --output temp/performance/collaboration.cpuprofile
```

Сигнального файла до запуска быть не должно. Profiler создаёт его сразу после Profiler.start; load harness начинает 30 секунд операций и удаляет сигнал. 35 секунд записи покрывают работу и ожидание последнего ACK. При подготовке и запуске барьера нагрузка остаётся ограничена минутой ожидания. Профилирование добавляет накладные расходы, поэтому такие задержки обозначаются как diagnostic и не используются для приёмки.

Профиль на той же сборке сохранён в `temp/performance/collaboration-c49c1ec-steady.cpuprofile`, сводка — в соседнем `.summary.json`. Получены 33250 samples за 35.12 с, из них 23.66 с active и 11.46 с idle. Inspector закрыт, независимая проверка порта прошла. Проценты ниже относятся к active samples; inclusive строки пересекаются и не складываются:

| Участок стэка | Доля active CPU |
| --- | ---: |
| Yjs encoding, все вызовы | 70.24% |
| strict validateDocument, включая encode | 54.68% |
| incoming shadow validation, включая encode | 49.91% |
| persistence, включая encode | 5.52% |
| model parsing | 2.74% |
| rich-text codec | 3.23% |
| GC | 5.75% |

Из общих 70.24% кодирования 32.80% приходятся на сверку canonical с кэшем, 33.76% — на валидированный shadow и 3.65% — на persistence. Среди exclusive функций выделяются CJS interop getter Yjs (16.49%), запись Item (8.45%), writeStructs (8.17%) и запись Content (6.86%). Сэмплирование показывает горячие стэки, а не точное число вызовов.

Повторная валидация при persistence не является основным расходом. Даже полное устранение её собственного model/rich-text обхода с обязательным сохранением точной бинарной сверки даст небольшую экономию: весь persist занял 5.52%, а необходимое кодирование внутри него — 3.65%. Усложнение границы валидации и ACK пока не обосновано этим профилем. Код сервиса при снятии профиля не менялся.
