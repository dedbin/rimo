# Десять активных соединений в одной комнате

`scripts/performance/active-room/run.mjs` — отдельный opt-in профиль R10: два реальных Chromium и восемь пишущих Node providers на одной новой доске. Каждый участник получает собственный существующий сетевой helper. Адрес приложения остаётся `http://localhost:3080`.

Это десять активных соединений и два переиспользуемых аккаунта: owner и anonymous editor. Восемь Node providers используют сессию owner; каждый Chromium получает отдельный процесс, контекст и свою сессию. Профиль не моделирует десять уникальных пользователей или десять браузеров с рендерингом. Он также не заменяет часовой профиль 50 соединений / 10 редакторов на пяти досках.

Сценарий подготовлен для независимого review. Сервисный запуск и численные результаты пока не получены; их нельзя выводить из узких тестов методики.

## Предварительные условия

Нужны зависимости проекта, Chromium для Playwright, существующий локальный Docker-стенд на порту 3080, приватный storage state тестового владельца и успешная текущая [калибровка сети](network-testing.md). Helper image должен быть собран и откалиброван заранее. Runner сам не собирает образы, не создаёт владельца и не перезапускает сервисы.

Профиль запускают только в согласованное свободное окно CPU. Десять helper имеют собственные лимиты памяти по 192 МиБ; к ним добавляются два Chromium и Node-генератор. Это дополнительная нагрузка на тот же host, а не имитация десяти отдельных компьютеров.

Команда из корня репозитория:

```powershell
node --import=tsx scripts/performance/active-room/run.mjs --allow-service-test --storage-state temp/performance/network-owner-storage.json --seconds 120 --label ACTUAL_IMAGE_AND_HOST
```

`--allow-service-test` обязателен. `--seconds` допускает 60–300 секунд, по умолчанию 120. Минимум выбран для получения хотя бы 50 завершённых браузерных операций в каждом направлении. `--compose-project` по умолчанию равен `rimo-rework` и используется только для чтения выбранных метаданных Docker. `--base-url` принимает только указанный локальный origin. `--help` ничего не запускает.

Результат получает новый путь `temp/performance/active-room/<UUID>/report.json`; существующий файл не перезаписывается при старте. `--output temp/performance/active-room/MY_RUN/report.json` позволяет указать собственный новый каталог запуска. Пароли, cookies и invite tokens не передаются через CLI. `--label` — короткая метка без секретов.

Состояние одного anonymous editor сохраняется отдельно в игнорируемом `temp/performance/active-room/guest-storage.json`. Аккаунт остаётся для следующего замера, поскольку публичное удаление гостей отключено. Приватное состояние входа не является отчётом.

## Сеть и проверка пути

Каждый из десяти участников использует свой private network namespace helper. Заданы 50 мс upstream и 50 мс downstream, а HTB ограничивает общий поток каждого участника до 50 Мбит/с в каждом направлении. Это десять отдельных лимитов; общий канал сервера не ограничивается одним общим пределом 50 Мбит/с.

Перед измерением runner требует:

- Полную успешную калибровку и совпадение текущего `networkSourceSha256`.
- Совпадение immutable image ID и configuration fingerprint каждого helper с калибровкой.
- Пять настоящих WebSocket RTT не менее 90 мс на каждом пути.
- Реальные классы `1:10` и `1:20` с `rate` и `ceil` по 50 Мбит/с; оба byte counter должны увеличиться между снимками вокруг активного окна и финального causal drain.
- Один CONNECT со статусом 200 для каждого Node provider и один успешный WebSocket Upgrade 101 для каждого Chromium. Chromium использует откалиброванный штатный HTTP proxy с `<-loopback>`; его внутренний ответ CONNECT не выдаётся CDP и отдельно не заявляется измеренным.

Для Node используется exact `https-proxy-agent@7.0.6` и общий `openProvider(..., { agent })`. Сам agent получает адрес собственного helper и выдаёт безопасное событие `proxyConnect`: сохраняется только код ответа. Отсутствие CONNECT, быстрый RTT, неверный HTB или неподвижный counter останавливают приёмку. Прямого fallback и CDP-имитации задержки нет. HTTP API-контекст каждого Node provider тоже проходит через его helper.

Первичная [README https-proxy-agent 7.0.6](https://github.com/TooTallNate/proxy-agents/blob/https-proxy-agent@7.0.6/packages/https-proxy-agent/README.md) описывает CONNECT и пример `ws` с `agent`. Сетевые ограничения, изоляция helper и исходная калибровка описаны в [network-testing.md](network-testing.md).

## Одновременная работа

Сцена использует общий fixture: 3000 объектов, 500 в viewport 1440×1000, 50 видимых image nodes и один уникальный небольшой asset. У десяти writers разные прямоугольники. Seed provider подтверждает начальную сцену и закрывается до открытия десяти участников. Он использует первый helper, но не занимает одиннадцатый room slot во время измерения.

Каждый Node provider записывает один настоящий Yjs commit с изменением `x` два раза в секунду и обновляет awareness десять раз в секунду. Два Chromium независимо выполняют реальные drag-жесты примерно раз в секунду, поочерёдно возвращая свой объект на исходное место. Начало окна общее. Пропущенные такты учитываются; генератор не воспроизводит их ускоренной серией.

Частота и максимальный интервал измеряются отдельно для каждого writer. Приёмка требует не менее 95% запланированного числа операций, не более 5% пропущенных тактов и отсутствия пауз длиннее трёх периодов, включая начало и конец окна. Для Node отдельно проверяется cadence awareness. Средняя частота всех участников не может скрыть остановившийся writer.

Примерно каждую секунду сохраняются число открытых соединений, pending causal operations, максимальный клиентский `bufferedAmount` и RSS/heap/event-loop задержка генератора. События закрытия и ошибки SDK сохраняют первую безопасную причину; reconnect не принимается за непрерывную работу. Сэмплирование не является чтением внутренних очередей сервера.

## Два разных измерения доставки

**Browser final DOM latency:** capture `pointerup` источника → изменение постоянного `style.transform` прямоугольника у другого Chromium. Временный drag preview не завершает таймер. Часы — `performance.timeOrigin + performance.now()` на одном host; отрицательная последовательность считается ошибкой. Это DOM-свидетельство, а не время появления пикселей compositor.

Получаются два направленных браузерных пути. Каждый должен содержать хотя бы 50 завершённых операций с p95 ≤ 300 мс. В отчёте сохраняются все попытки, незавершённые операции и отметка попадания `pointerup` внутрь активного окна; поздняя или потерянная операция не исчезает из отчёта ради меньшего p95.

**Node causal latency:** момент перед локальной транзакцией → `afterTransaction` у другого Node provider, чей Yjs state vector уже включает конечный clock именно этой операции. Постороннее update-событие этого не доказывает. При доставке нескольких операций одним сообщением каждая подтверждается отдельно; повторное наблюдение не удваивает количество.

Получаются 56 направленных Node-пар. Для каждой проверяются все ожидаемые доставки и p95 ≤ 300 мс. Pending операции не удаляются по таймеру; после остановки writers есть ограниченный 20-секундный causal drain, а недоставленные изменения остаются ошибкой. Это не измерение всех 90 возможных направлений между десятью участниками. Доставка Node-правок в DOM браузеров проверяется в финальном состоянии, без приписывания ей отдельного latency p95.

## Saved, финальная сходимость и аудит

Во время непрерывной работы восьми Node writers runner не ждёт Saved после каждого жеста: документ может меняться раньше следующего ACK. Все десять writers сначала прекращают новые правки. Затем проверяются точный persisted snapshot каждого Node provider, конечные координаты всех десяти объектов в обоих браузерах и Saved у обоих Chromium.

Все десять участников закрываются до финального аудита. Новый Node provider через первый helper получает документ и проверяет все 3000 координат, размер сцены и соответствующий persisted ACK. Это свежий клиент и проверка подтверждённого состояния; сервис не перезапускается, поэтому холодное чтение после рестарта PostgreSQL здесь не заявляется.

`status: accepted` требует все критерии, отсутствие runtime errors и полностью успешную очистку. `not-accepted` содержит фазу, первую безопасную причину и частичные измерения. `interrupted` и `cleanup-failed` не означают завершённую приёмку. Report содержит commit/dirty, версии зависимостей и браузеров, source SHA-256, helper image IDs, выбранные образы/лимиты сервисов и калибровку. `Config.Env` не читается; значения cookies, emails, invite secrets и тела WS не сохраняются.

## Прерывания и очистка

Общий проверенный network lifecycle обрабатывает SIGINT, SIGTERM и deadline `(seconds + 480)` секунд. `RIMO_NETWORK_DEADLINE_MS` позволяет сократить предел. Встроенные signal handlers Playwright отключены, чтобы общий `finally` мог завершить очистку. При локальном сбое активного окна закрываются все его consumers, а первый сбой сохраняется. Ошибка одного шага cleanup не пропускает остальные.

До создания каждого helper его случайный UUID label записывается в report. Очистка общего helper сверяет ровно этот label и известный container ID, после чего удаляет только собственный контейнер и cidfile. Основной Compose, его тома, `.env`, firewall, DNS и системные настройки runner не меняет. Удаляются только новая тестовая доска и собственные consumers/helpers/API-контексты. Выходной каталог и отчёт сохраняются; recursive удаления host-каталогов нет.

Сигнал во время итоговой записи заменяет результат на interrupted и ненулевой exit code; failed cleanup имеет отдельный статус. Внешний SIGKILL или Windows `TerminateProcess` перехватить нельзя: оператор использует сохранённые `helperAttempts`, `helpers` и `createdBoards` для точной ручной очистки, не затрагивая другие запуски.

Узкая проверка методики без приложения, Docker и браузера:

```powershell
npx vitest run __tests__/active-room-harness.test.ts --maxWorkers 1
```

Она проверяет реальные Yjs clocks, объединённую доставку, отсутствие дубликатов и отбрасывания поздних операций, cadence каждого writer, сетевые критерии, неполные отчёты и opt-in. Эти проверки не являются результатом сервисного профиля.
